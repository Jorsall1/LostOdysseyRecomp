FINDING 3 - CORRECTION: the audio starvation is a SYMPTOM of the GPU stall.
  45,000 submitted frames x 256 samples / 48,000 Hz = exactly 240 s of audio in
  a 591 s run. 591.7 - 346.7 s of stalls = 245 s of non-stalled time. The guest
  produced ~1 frame per 5.33 ms of NON-STALLED wall time and nothing during the
  stalls. Corroborating: queued=6144 B = 3 frames (under kQueuedFrames=8),
  queue_drops=0, queue_errors=0 - the queue was never full, never capped, never
  erroring. clock_resets=7 is the driver re-anchoring after each host stall.
  => The Entry 1 task-2 change (kQueuedFrames / kBoundedDrainWait /
     kDrainStallTimeout) CANNOT have fixed the loading-screen pause, because
     the drain wait was never what blocked. It is harmless and still correct
     for a genuine "output stops pulling" case, but must not be credited with
     this fix. Fix the WAIT_REG_MEM stall and starved= collapses on its own.

FINDING 4 - decoding WAIT_REG_MEM mem 0x10002 ref 0x0 mask 0xffffffff value 0x4.
  pollRegAddr & ~3 = guest physical 0x10000; & 3 = endian 2 (8in32);
  waitInfo & 7 = 3 (equal), ref 0. This is the D3D present sync block, the
  sequence documented in docs/archive/2026-09-04/gpu.md:
    WAIT mem[blk+4]==1 ; WAIT mem[blk+0]==4   <- CPU Present wrote the mask
    INTERRUPT cpu_mask=4                      <- PM4_INTERRUPT -> DispatchInterrupt(1,2)
    WAIT mem[blk+0]==0 ; WAIT mem[blk+4]==0   <- GPU waits for the ISR to clear
  The block sits at 0x10000 this run (0xB000 previously). value 0x4 = the CPU
  mask is still set: the CP is waiting for the guest interrupt handler to clear
  it, and the handler has not run.

  The "views" line is AMBIGUOUS and was not overstated:
    polled 0x4 views: A 0x4 @ 0xa0010000  C 0x0 @ 0xc0010000  E 0x0 @ 0xe0011000
  (a) Broken alias - guest writes via C/E, CP reads A (TranslatePhysical =
      0xA0000000 + (phys & 0x1FFFFFFF)). Supported by the ResolveFrameView
      comment in audio.cpp ("under Backend::Heap the two views of a physical
      buffer are no longer the same pages"), which CONTRADICTS docs/SWITCH.md
      and guest_address_space.cpp. But a dead page would never become 0, and
      the frame did finish after 139 s - so (a) cannot explain recovery.
  (b) The ISR never ran - A 0x4 is the live value, C/E are separate zero pages
      nobody writes; the wait ends when the GPU Interrupt thread finally runs
      the callback. This FITS the 139 s recovery. Leaning to (b).

FINDING 5 - concrete mechanism for (b): priority inversion.
  * InterruptMain() and VsyncMain() in gpu/command_processor.cpp set NO thread
    priority, unlike WorkerMain (PreferPerformanceCores), DriverMain (0x2C) and
    MonitorMain (0x2B). They run at the default pthread priority (0x3B per the
    audio.cpp comment), BELOW the guest's threads. Horizon schedules strictly
    by priority on three cores, so during a loading screen (render_fence::
    LoadBoost, movie/XMA decode, XAudio workers) the 0x3B interrupt thread can
    be starved indefinitely while the waiter holds a performance core.
  * std::this_thread::yield() in the poll loop (when wait < 0x100) is the
    amplifier: on Horizon yield donates only to threads of EQUAL OR HIGHER
    priority, so it can never let a 0x3B thread run. The CP spins forever on a
    thread it is structurally preventing from running. Explains "intermittent,
    at the loading screen" exactly.

SHUTDOWN LOGIC - remaining gaps (mechanism itself is sound; stderr.log confirms
  the right path: "leaving through libnx's application exit", so std::exit(0)
  runs and the atexit handlers fire before fsdevUnmountAll):
  * std::atexit is LIFO and shares its chain with static destructors. Any
    __cxa_atexit destructor registered after the first Present (lazy
    function-local statics in the logger, SDL, plume) runs BEFORE StopMonitor.
    If the log sink dies first while the monitor is inside LOG_NOTICE, join()
    deadlocks and Horizon kills the process after ~15 s - same dialog, new cause.
  * The 500 ms wait in StopDriverThread can expire if the driver is inside a
    guest XAudio callback (the KfAcquireSpinLock stalls in SWITCH-BENCHMARKS.md
    reached 5 s). Memory-safe (every g_stream use holds g_deviceMutex and
    null-checks) but not the guarantee the task asked for.
  * td214/t25b5 are NOT the only card writers. Also writing: the logger's own
    1 s flush; the hang watchdog and crash handler via RawAppend (own FS
    session); cpu-samples.bin; the heap census; PGO profile writes on quit; the
    debug server's shot; and - confirmed this entry from os/log_collection.cpp -
    StartUpload(), which .detach()es a thread that sleeps 5 s, then writes
    log-collection-sent and a LOG_INFO line. That is a THIRD unguarded writer.
  * Convergent fix: one g_logClosed latch in os/logger.cpp (a .cpp) that
    no-ops every LOG_* after a final flush. Then "zero background threads write"
    holds regardless of which thread is alive, and the per-module ShuttingDown()
    guards become belt-and-braces rather than the mechanism.
  * The 4 s watchdog path in stderr.log ("if it does not finish in 4 s the
    process ends here") bypasses atexit entirely.
  * Minor: os/detach_thread.h is now an unused include in perf_stats.cpp;
    apu::Init() has no re-entry guard on g_thread.
