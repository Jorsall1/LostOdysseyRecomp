FINDING A - NO CHANGE IS POSSIBLE OR NEEDED IN guest_address_space_switch.cpp
================================================================================
The user asked for a patch there so that "writes to View A are immediately
recognized". The file's own code refutes the premise:
  * On __SWITCH2__ the backend is Backend::Heap. kaiHEN 20261116 title takeover
    runs the NRO inside a donor title whose NPDM syscall mask contains 0x73,
    0x74, 0x75, 0x77, 0x78 and 0x51; a masked svc* TERMINATES the process rather
    than returning an error, so no mapping syscall may be used at all. The whole
    4 GiB window is therefore ONE memalign() block.
  * Its own comment: "C and E are distinct ranges of the block now, not hardware
    aliases of A: a write through A no longer shows up through C or E."
  => The stall line "A 0x4 @ 0xa0010000  C 0x0 @ 0xc0010000  E 0x0 @ 0xe0011000"
     means only: A holds the live value 0x4, and C/E are two unrelated zeroed
     ranges of the same block. It is NOT evidence of an aliasing failure.
  * CommandProcessor::TranslatePhysical already reads A
    (0xA0000000 + (phys & 0x1FFFFFFF)); the poll loop already uses
    volatile uint32_t*; ARM64 data caches are coherent across cores. The write
    IS recognised immediately.
  * Decisive: reading (a) "broken alias" cannot explain the observed recovery -
    a dead mapping never becomes 0, yet the swap-12500 frame did finish after
    139 s. Reading (b) "the ISR never ran" does.
  This supersedes the ambiguity recorded in summary_002 FINDING 4.

================================================================================
FINDING B - ROOT CAUSE OF THE WAIT_REG_MEM 0x10002 STALL: PRIORITY INVERSION
================================================================================
Packet decode (confirmed against docs/archive/2026-09-04/gpu.md): pollRegAddr
0x10002 -> physical 0x10000, endian 2 (8in32); waitInfo & 7 == 3 (equal), ref 0;
value 0x4 is the CPU mask PM4_INTERRUPT raised, which the GUEST INTERRUPT
HANDLER must clear. Two defects in gpu/command_processor.cpp stop it running:

  1. InterruptMain() and VsyncMain() set NO thread priority.
     WorkerMain calls os::scheduling::PreferPerformanceCores(); apu::DriverMain
     sets 0x2C; perf_stats::MonitorMain sets 0x2B. These two set nothing and run
     at the default pthread priority, BELOW the game's own threads. Horizon
     schedules strictly by priority across three cores, so a loading screen
     (render_fence::LoadBoost, movie/XMA decode, XAudio workers) starves the one
     thread the GPU is blocked on.
  2. std::this_thread::yield() in the WAIT_REG_MEM poll loop (taken whenever the
     packet's wait field is < 0x100). On Horizon yield() donates only to threads
     of EQUAL OR HIGHER priority, so it can never let the lower-priority
     "GPU Interrupt" thread run. The CP spins a performance core waiting on a
     thread it is itself preventing from being scheduled. This explains the
     intermittent, loading-screen-specific nature exactly.

CHANGES APPLIED - gpu/command_processor.cpp
================================================================================
  * Added #include <os/switch_platform.h> inside the existing
    #if LO_PLATFORM_SWITCH include block (a new include only; no header edited).
  * New helper GuestCallbackThreadPriority() (LO_PLATFORM_SWITCH only):
    returns 0x2B by default - above the game's threads and the audio driver
    (0x2C), below SDL's audio output (0x2A) - clamped to 0x00..0x3F and
    overridable at runtime with LO_GPU_ISR_PRIORITY. The override exists because
    the tree's own comments disagree about whether guest threads sit at 0x2C
    (perf_stats.cpp) or 0x3B (audio.cpp), so the value stays tunable on hardware
    without a rebuild.
  * InterruptMain(): SetCurrentThreadPriority(GuestCallbackThreadPriority()) at
    entry, with the full rationale in a comment citing the 216.990 s stall.
  * VsyncMain(): the same - it also runs the registered interrupt callback.
  * WAIT_REG_MEM poll loop: no longer spins on Switch. kMinimumPollMs is 1 on
    LO_PLATFORM_SWITCH and 0 elsewhere, so the wait always takes the
    m_waitProgress condition-variable path with at least a 1 ms sleep. A
    completed interrupt still wakes it immediately via m_interruptsCompleted, so
    the normal case costs nothing. Desktop behaviour (yield when wait < 0x100)
    is byte-for-byte unchanged.
  * Stall diagnostics: new second warning line
      "  interrupt handler: completed=.. pending=.. callback=.. poll_ms=..
       self_waits=.. stage=.. swap=.."
    m_pendingInterrupts.size() is read under m_interruptMutex, which is released
    before GetInterruptCallbackSnapshot() is called (it takes the same mutex).
    pending>0 with completed frozen confirms starvation; pending==0 with no
    callback means no interrupt is outstanding at all.
  * Views line corrected under #if defined(__SWITCH2__): prints view A only and
    states that C and E are separate ranges of the same heap block, not aliases.
    The three-view line is preserved verbatim for the mapping backends. This
    stops the next session being spent on a non-existent aliasing bug.
