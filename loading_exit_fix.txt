The audio hole: "frames submitted" climbs, peak stays 0
------------------------------------------------------
A guest pointer argument reaches an import as base + address
(kernel/function.h, ArgTranslator::GetValue for pointer types:
reinterpret_cast<T>(base + uint32_t(v))). The view the guest named in the
register is the view that is read - there is no Translate() in that path.

On the desktop hosts that is harmless because the A window is the same memory
at offset 0, so 0x1A000000 and 0xBA000000 are the same bytes. Under
Backend::Heap they are separate pages: the physical pool lives at
0xA0000000..0xC0000000 and low guest RAM is ordinary host memory. A render
driver that submits the *masked physical* address of its frame (0x1A000000 for
a buffer that lives at 0xBA000000) therefore has its own mix read as zeroed
guest RAM. The guest mixer keeps running, apu::SubmitFrame keeps counting
frames, and peak stays exactly 0 - which is the log line we have.

Fix (apu/audio.cpp): ResolveFrameView in SubmitFrame.
  * While no frame has ever carried a sample, the submit path checks both
    views. FrameLooksLikeAudio requires a non-zero buffer whose samples are
    finite and inside +/-16 (a real mix), so half-written or random pool data
    is not followed.
  * If the submitted view is empty and the A window at 0xA0000000+(p&0x1FFFFFFF)
    holds audio, that view is used from then on and one line is logged:
        audio: submitted frame at 0x1a000000 is empty; its audio is at
        0xba000000 in the A window (masked physical address read in the other
        view under Backend::Heap)
  * If the guest later names a buffer that really does hold its mix, the code
    goes back to the submitted view, so this cannot latch onto a stale pool
    page.
  * True guest silence (both views empty) is left alone: the game's own silent
    frames stay silent.

The loader probe (ppc_recomp.24.cpp, sub_82485030)
--------------------------------------------------
This is the .cpp of the recompiled function the dump points at, so the probe
sits exactly on the loop that never finishes:

    [load] [Guest Main] still waiting on entry=0x........ vtable=0x........
           slot288=0x........ cursor=N count=M (N busy spins)

logged at most once every 16384 spins (a second or so), naming the object, its
vtable and the slot that keeps answering "busy" - that is the job the loading
screen is waiting for. And the advance line, once the queue drains after having
been busy:

    [load] [Guest Main] pending list drained: cursor=N count=M, N busy spins,
           N busy reports so far

Both go to stderr, so they land in stderr.log, exit.log's neighbour, and the
network log. The next run therefore answers the question directly: which
object blocks, or whether the drain is always empty (meaning the wait is a
flag set elsewhere and the slot never even asks).

PART 2 - THE EXIT THAT DROPPED kaiHEN's R -> hbmenu HOOK
=====================================================================
What our exit did (os/switch/switch_runtime.cpp, EndProcessToHbmenu):
      QuiesceAudio()            (apu::SetPaused(true) + apu::xma::Shutdown())
      os::logger::DrainForExit(); fflush(stdout/stderr)
      __nx_win_exit()           <-- closes the window and display ourselves
      appletUnlockExit()
      std::exit(0)

What libnx's own exit does - disassembled from this ELF, __libnx_exit at
0x6091c0:

      0x6091c8  bl  __appExit            (applet teardown: appletExit, i.e. the
                                         Exit that tells am the applet leaves)
      0x6091ec  bl  __nx_gpu_exit
      0x6091fc  bl  __nx_win_exit        (closes the vi layer and display)
      0x609200  bl  _serviceGuardCloseAll
      0x609210  bl  _gsvSyncExit
      0x609214  bl  _threadReleaseExited
      0x609218  bl  envGetExitFuncPtr
      0x609224  bl  __nx_exit            (svcExitProcess)

So std::exit(0) already ran the entire applet teardown, including the
__nx_win_exit we were calling by hand a moment earlier. That early call is the
one thing this path did that no ordinary homebrew exit does: it tears the
applet's window/display down before libnx sends the applet Exit, which is a
plausible way to leave kaiHEN's takeover state inconsistent - exactly the
14:47:32 symptom (exit_code=0 at 111.765 s, then holding R on a game no
longer opened hbmenu).

Change:
  * No __nx_win_exit() on __SWITCH2__. The exit is now precisely libnx's:
    appletUnlockExit() first (so am's 15 s forced-termination timer can never
    start during the teardown - libnx requires the unlock before the process
    ends), then std::exit(0), which runs __appExit -> appletExit ->
    __nx_win_exit -> service teardown -> svcExitProcess.
  * One line in stderr for the next run:
        [exit] leaving through libnx's application exit (applet type N, exit
        lock released)
    The applet type tells us whether kaiHEN's takeover presented this as an
    Application (0) or something else, which decides the next step if the hook
    is still lost.
  * Audio is still quiesced and the logs are still drained before that, so
    neither audio thread is inside audren or guest memory during the teardown,
    and exit.log keeps its trail.

Note on the earlier removals: ISelfController::Exit stays out. The 2026-11-16
system error dialog came from svcExitProcess with appletLockExit still held (now
impossible: the unlock is the first thing the teardown does), not from the Exit
request itself - that distinction is why this run keeps libnx's own teardown
instead of hand-rolling one.
